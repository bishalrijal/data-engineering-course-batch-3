Virtual Environments

sample_data_loader.py needs psycopg2-binary, Faker, and python-dotenv. Some other project on your machine might need a different, maybe incompatible, version of one of those. A virtual environment is what keeps those two facts from ever becoming a problem — a private, disposable copy of just the packages one project needs, that doesn't touch anything else on the machine.

What a venv actually is

python3 -m venv .venv creates a folder containing its own Python interpreter and its own empty site-packages directory. Activating it doesn't install anything — it just rewrites your current shell's PATH so that python and pip resolve to the copies inside .venv/ instead of the system ones. deactivate puts your PATH back. Nothing about your system Python ever changes.

The workflow

$ python3 -m venv .venv                    # create -- makes a .venv/ folder
$ source .venv/bin/activate                # activate (Windows: .venv\Scripts\activate)
(.venv) $ pip install -r requirements.txt  # install this project's dependencies
(.venv) $ pip freeze > requirements.txt    # snapshot exact versions, if you changed them
(.venv) $ deactivate                       # back to your normal system Python

The (.venv) prefix most terminals add to your prompt is the tell — if it's not there, nothing is activated and pip install is about to land somewhere you didn't intend.

Try it: the same install, with and without a venv

Without an active venv, pip install lands in the system Python — visible to, and shared by, every project on the machine.

$ pip install psycopg2-binary==2.9.5

With a venv active, pip install only touches that project's own folder. The system Python, and every other project's venv, is untouched.

$ python3 -m venv .venv
$ source .venv/bin/activate
(.venv) $ pip install psycopg2-binary==2.9.5

Common mistakes

MistakeWhat goes wrongFix
Installing before activatingpip install lands in the system Python, defeating the entire point of the venvCheck for (.venv) in your prompt, or run which python3, before installing
Committing .venv/ to gitThousands of binary files, different on every OS, bloat the repo for no reasonAdd .venv/ to .gitignore (already done in this repo)
pip freeze > requirements.txt from a cluttered venvDebugging tools and one-off packages you installed end up required for everyone else tooKeep requirements.txt to your project's real dependencies; freeze from a clean venv
Editor still pointing at the system PythonModuleNotFoundError for a package you're sure you installedExplicitly select the venv's interpreter in your editor (VS Code: "Python: Select Interpreter")
Two terminal tabs, only one activatedThe exact same script "works" in one tab and fails in the otherActivation is per-session — re-run source .venv/bin/activate in every new tab
