Concept 1 of 6

Regular expressions

A support ticket body is free text — a customer types whatever they want. Before you can safely store or embed it, you need to find things inside it: a credit card number, a phone number, an email signature, a boilerplate line like "Sent from my iPhone". Regular expressions (regex) are the standard tool for describing "text that looks like this" as a pattern instead of an exact string.

The building blocks

A regex is a small pattern language. A handful of tokens cover almost everything you'll need:

TokenMatchesExample
\dA single digit\d\d\d matches "555"
\wA letter, digit, or underscore\w+ matches "hello_123"
\sWhitespace (space, tab, newline)\s+ matches one or more spaces
\bA word boundary (not a character itself)\bcat\b matches "cat" but not "category"
+ / * / ?One-or-more / zero-or-more / optional\d{3}[-.\s]\d{4} — quantities and alternatives
{m,n}Between m and n repetitions\d{13,16} matches a 13–16 digit card number

Compile, search, substitute

In Python, you build a pattern once with re.compile() and reuse it — this is exactly what the pipeline's PII scrubber does.

pythonthe pattern behind PII redaction
import re

# A run of 13-16 digits, optionally separated by spaces/dashes
CARD_RE  = re.compile(r"\b(?:\d[ -]*?){13,16}\b")
# 3 digits, separator, 3 digits, separator, 4 digits
PHONE_RE = re.compile(r"\b\d{3}[-.\s]\d{3}[-.\s]\d{4}\b")

text = "My card 4111 1111 1111 1111 was charged, call 555-123-4567"

# .search() tells you IF and WHERE a pattern matches
if CARD_RE.search(text):
    print("Found a card number")

# .sub() replaces every match
text = CARD_RE.sub("[REDACTED_CARD]", text)
text = PHONE_RE.sub("[REDACTED_PHONE]", text)
print(text)
# "My card [REDACTED_CARD] was charged, call [REDACTED_PHONE]"

Before / After — exact strings vs. patterns

pythonproblem: only catches the exact formats you thought of
text = text.replace("555-123-4567", "[REDACTED]")
text = text.replace("4111 1111 1111 1111", "[REDACTED]")

# Next customer writes "555.123.4567" or "4111-1111-1111-1111"
# → neither is caught. PII leaks straight into the embedding.
pythonsolution: describe the shape, not one instance
PHONE_RE = re.compile(r"\b\d{3}[-.\s]\d{3}[-.\s]\d{4}\b")
# [-.\s] matches a dash, dot, OR whitespace — one pattern,
# every separator style a customer might type.

for phone in ["555-123-4567", "555.123.4567", "555 123 4567"]:
    print(bool(PHONE_RE.search(phone)))   # True, True, True
⚠️
Order matters. If you clean whitespace after matching a boilerplate phrase like "sent from my iphone", an extra space introduced anywhere in that phrase (even by an unrelated cleaning step) will make a single-space pattern silently fail to match. Normalize whitespace before running boilerplate/signature patterns, not after.
Concept 2 of 6

Rich text & HTML

A support ticket doesn't arrive as clean plain text. Real helpdesk software — Zendesk, Freshdesk, Intercom — submits ticket bodies from a rich-text editor, which means the body you receive is HTML: paragraphs, bold text, links, bullet lists, email signatures, and quoted reply chains from earlier messages in the thread. Before you can embed this text for search, you need to turn it back into plain language.

What a real ticket body looks like

htmlraw body, straight from the ticket form
<p>My card 4111 1111 1111 1111 was charged twice, call me at 555-123-4567.</p>
<br>--<br>Jamie Rivera<br>
<a href="mailto:jamie@personalmail.com">jamie@personalmail.com</a>
<blockquote class="gmail_quote">On Mar 3, Alex Chen wrote: ...</blockquote>

Buried in there is the one sentence that actually matters for search — everything else (the signature, the quoted thread) is noise that will confuse a search index if left in.

Why regex can't safely strip this

It's tempting to strip tags with a regex like re.sub("<[^>]+>", "", html). This breaks on real-world HTML: unclosed tags, tags nested inside other tags, and HTML entities (&amp;, &nbsp;) that need decoding, not deleting. HTML is not a regular language — matching nested structure reliably needs an actual parser.

pythona real parser, not string surgery
from bs4 import BeautifulSoup

def strip_html(raw: str) -> str:
    soup = BeautifulSoup(raw, "html.parser")

    # Drop tags whose CONTENT should never reach a search index
    for tag in soup(["script", "style"]):
        tag.decompose()

    # Drop quoted prior messages — pure noise for semantic search
    for quote in soup.find_all("blockquote"):
        quote.decompose()

    # get_text() also decodes entities: &amp; -> &, &#39; -> '
    return soup.get_text(separator=" ")

Before / After — regex vs. a real parser

pythonproblem: breaks on real inboxes
import re
text = re.sub(r"<[^>]+>", "", html)

# html = "<p>Wrong item</p><style>.x{color:red}</style>"
# → "Wrong item.x{color:red}"  — the CSS text leaks straight through,
#   because regex deleted the tags but not what they wrap.
# A missing closing tag ("<p>text") breaks the pattern entirely.
pythonsolution: parse structure, then extract text
html = '<p>Wrong item</p><style>.x{color:red}</style>'
soup = BeautifulSoup(html, "html.parser")
for tag in soup(["style"]):
    tag.decompose()          # removes the CSS text WITH its tag
print(soup.get_text())     # "Wrong item" — clean

# Malformed HTML ("<p>text" with no closing tag)?
# The parser tolerates it and still returns "text".
💡
get_text(separator=" ") inserts a space at every tag boundary — a phrase split across tags (e.g. a bolded word inside "Sent <strong>from</strong> my iPhone") comes back with doubled spaces. Normalize whitespace with re.sub(r"\s+", " ", text) right after parsing, before running any further pattern matching.
Concept 3 of 6

Embeddings & similarity

"Semantic search" means finding tickets that mean the same thing as a query, even if they don't share a single word — "can't log in" should find "password reset broken". That requires turning text into vectors (lists of numbers) positioned so that similar meanings land close together, then measuring "close together" mathematically.

From words to numbers: a pretrained sentence model

The simplest approach — TF-IDF (term frequency–inverse document frequency) — scores each ticket by which words it contains: common words across the whole dataset ("the", "please") get a low weight, rare-but-frequent-in-this-ticket words ("refund", "crashes") get a high weight. It's a real baseline, but it only ever measures shared vocabulary — two tickets with zero words in common score as completely unrelated, even if they describe the exact same problem.

A pretrained sentence embedding model solves that differently: instead of counting words, it's a neural network already trained (by someone else, on huge amounts of text) to place sentences with similar meaning near each other in vector space — regardless of which specific words were used. You don't train anything; you just call the model.

pythontext → vector, with an open-source model
from sentence_transformers import SentenceTransformer

# Downloaded once from the Hugging Face Hub (~90MB), then cached locally —
# no API key, no per-call cost, no network needed on later runs.
model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

texts = [
    "I can't log in, password incorrect",
    "Forgot password email never arrives",
    "My order hasn't shipped yet",
]

embeddings = model.encode(texts, normalize_embeddings=True)
print(embeddings.shape)   # (3, 384) — 3 tickets, one 384-number vector each

One model call replaces TF-IDF's two-step process (build a vocabulary-sized vector, then compress it down). The model was already trained so that its 384-number output is a compact, meaning-aware embedding — nothing to fit on your own dataset first.

Measuring "similar": cosine similarity

Once every ticket is a vector, similarity between two tickets is the angle between their vectors — not the distance. Two vectors pointing in almost the same direction represent similar meaning, regardless of length. This is cosine similarity, and it's just a dot product once both vectors are unit length:

pythoncosine similarity, step by step
import numpy as np

# normalize_embeddings=True above already L2-normalized every vector
# to length 1 — so a plain dot product between two of them IS the
# cosine of the angle between them: 1.0 = identical meaning, 0 = unrelated.
similarity = np.dot(embeddings[0], embeddings[1])
print(similarity)   # e.g. 0.61 — "can't log in" and "forgot password" are related
#                     even though they share only one real word ("password")

pythonproblem: misses every paraphrase
query = "cant log in, password reset broken"

pythonsolution: compare meaning, via vectors
query_vec = embed_query("cant log in, password reset broken")

scores = embeddings @ query_vec   # cosine similarity vs. every ticket
best = np.argsort(-scores)[:5]

# "Forgot password email never shows up in my inbox" scores 0.71 —
# no shared words, but the vectors point in nearly the same direction.
💡
Why an open-source Hugging Face model, and not a paid API? sentence-transformers/all-MiniLM-L6-v2 runs entirely on your own machine — no API key, no per-call cost, and no data ever leaves the box. It downloads once (~90MB) and every run after that is fully offline. A hosted embeddings API (OpenAI, Anthropic) can produce higher-quality vectors at the cost of latency, spend, and sending ticket text to a third party — swapping to one later touches only embed.py, since the rest of the pipeline just expects "a fixed-size vector in, a fixed-size vector out."
⚠️
TF-IDF isn't obsolete. It's cheaper to compute, needs no model download, and is easier to debug (you can point at exactly which shared word drove a match). For a support desk where customers mostly reuse the product's own terminology, it can be good enough. Neural embeddings earn their cost when paraphrasing is common — which, for free-text customer complaints, it usually is.
Concept 4 of 6

SQL keys & upserts

Every stage of the pipeline reads from one table and writes to another — raw tickets, validated tickets, cleaned chunks, embeddings. Two relational-database ideas make that reliable in a way a Python list or a flat file never can: primary keys that make duplicates impossible, and upserts that make re-running the pipeline safe.

Primary keys: let the database refuse duplicates

Instead of tracking "have I seen this ID before?" with a Python set, a PRIMARY KEY constraint makes the database itself reject a duplicate — it can't be forgotten or skipped by a bug in application code.

sqla constraint instead of a Python set
CREATE TABLE tickets_validated (
    ticket_id TEXT PRIMARY KEY,   -- no two rows can share a ticket_id
    body TEXT,
    category TEXT
);

-- Inserting a ticket_id that already exists raises an error —
-- the constraint is enforced by Postgres, every time, no exceptions.

Upserts: rerun safely

A ticket gets edited, or you fix a bug in the cleaning logic and want to reprocess. You don't want to wipe the whole table and start over, and you don't want a plain INSERT to fail because the row already exists. ON CONFLICT ... DO UPDATE — an upsert — does the right thing either way: insert if new, update if it already exists.

sqlinsert-or-update in one statement
INSERT INTO tickets_validated (ticket_id, body, category)
VALUES (%s, %s, %s)
ON CONFLICT (ticket_id) DO UPDATE SET
    body     = EXCLUDED.body,
    category = EXCLUDED.category;

-- Run this pipeline once, or a hundred times, on the same data:
-- the table ends up in exactly the same state either way.

Before / After — Python-side dedup vs. a database constraint

pythonproblem: reprocesses everything, every time
conn.execute("TRUNCATE ticket_chunks")
for record in all_validated_records:
    insert_chunk(record)   # re-inserts every row, even unchanged ones

# Fine for a small nightly batch. At scale, this means
# re-cleaning and re-embedding millions of unchanged tickets
# just to pick up ten edited ones.
pythonsolution: upsert on the natural key
for record in all_validated_records:
    cur.execute("""
        INSERT INTO ticket_chunks (chunk_id, text)
        VALUES (%s, %s)
        ON CONFLICT (chunk_id) DO UPDATE SET text = EXCLUDED.text
    """, (record.chunk_id, record.text))

# Unchanged rows: a no-op update. Changed rows: updated in place.
# New rows: inserted. One statement handles all three cases.
⚠️
Not every table wants an upsert. A landing zone that holds raw, as-ingested data is usually fine to fully refresh (TRUNCATE + re-insert) each run — it's a copy of the source, not a record you're incrementally correcting. Reserve upserts for tables downstream that represent "the current best version of this record."
Concept 5 of 6

Vector databases

Once every ticket is a vector, you need somewhere to store all of them and a fast way to ask "which vectors are closest to this one?". A vector database answers that question at scale. pgvector is a Postgres extension that adds a vector column type and nearest-neighbor search directly into a database you already know — no separate service to run and keep in sync.

A column type for vectors

sqlenabling pgvector
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE ticket_embeddings (
    chunk_id  TEXT PRIMARY KEY,
    embedding vector(384)   -- a fixed-size numeric vector, stored as a real column
);

Distance operators

pgvector adds operators that compute distance between two vectors directly in SQL. This project's embeddings are L2-normalized, so cosine distance (<=>) is the natural fit — similarity = 1 - distance.

OperatorDistance metric
<->Euclidean (L2) distance
<=>Cosine distance
<#>Negative inner product
sqlnearest neighbors, in SQL
SELECT chunk_id, text, 1 - (embedding <=> %s) AS score
FROM ticket_embeddings
JOIN ticket_chunks USING (chunk_id)
ORDER BY embedding <=> %s
LIMIT 5;
-- %s is the query vector, bound once and reused for both the
-- score calculation and the ORDER BY that finds the nearest rows

Indexing for scale

At a few hundred rows, comparing the query against every row (a sequential scan) is instant. At millions of rows it isn't — you need an approximate-nearest-neighbor index, like HNSW, so Postgres can find the closest vectors without checking all of them.

sqlan index built for this exact query shape
CREATE INDEX ON ticket_embeddings
    USING hnsw (embedding vector_cosine_ops);
-- vector_cosine_ops here MUST match the <=> operator used in queries —
-- an index built for one distance metric won't be used for another.

Before / After — searching in Python vs. in the database

pythonproblem: doesn't scale past what fits in memory
all_rows = cur.execute("SELECT * FROM ticket_embeddings").fetchall()
# every embedding, loaded into a Python process, every query

scores = [cosine_sim(row.embedding, query_vec) for row in all_rows]
top5 = sorted(zip(scores, all_rows))[-5:]
# fine at 300 rows; falls over long before 10 million
pythonsolution: let the database + index do the work
cur.execute("""
    SELECT chunk_id, 1 - (embedding <=> %s) AS score
    FROM ticket_embeddings ORDER BY embedding <=> %s LIMIT 5
""", (query_vec, query_vec))
top5 = cur.fetchall()
# Postgres uses the HNSW index; only ever returns the 5 rows you need
Concept 6 of 6

Docker & docker-compose

This pipeline needs a Postgres database with the pgvector extension installed — something most machines don't have out of the box, and something you don't want to hand-install and configure differently on every laptop. Docker packages a piece of software and everything it needs to run into one reproducible unit; a container is that unit, running.

Declaring a service with docker-compose

docker-compose.yml describes what to run, declaratively: which image, which ports, which environment variables, and which data should survive a restart.

yamldocker-compose.yml
services:
  postgres:
    image: pgvector/pgvector:pg16      # Postgres, with pgvector already installed
    environment:
      POSTGRES_DB: support_tickets
      POSTGRES_USER: pipeline
      POSTGRES_PASSWORD: pipeline
    ports:
      - "5433:5432"                    # host_port:container_port
    volumes:
      - pgdata:/var/lib/postgresql/data  # named volume — survives container restarts

volumes:
  pgdata:

The commands you'll actually run

CommandWhat it does
docker compose up -dStart the service in the background
docker compose psCheck whether it's running (and healthy)
docker compose logsSee what the container has printed
docker compose downStop and remove the container (data survives — it's in the volume)
docker compose down -vStop and delete the volume — all data is gone
⚠️
Port mapping reads right-to-left in your head, left-to-right on the page. "5433:5432" means: the container's internal Postgres (always on 5432) is reachable from your machine on 5433. If a machine already runs a native Postgres on the default port 5432 — common in a course environment with other projects — mapping the container to a different host port avoids a conflict entirely.
💡
The volume is the database. The container itself is disposable — stop it, delete it, recreate it, and as long as the named volume (pgdata) still exists, your data is untouched. down -v is the one command that actually deletes it, which is why it's worth pausing before you run it.

Where each concept lives in the pipeline

  • Regular expressions: validate.py redacts card numbers, phone numbers, and emails; clean_transform.py strips boilerplate signatures with the same tool
  • Rich text & HTML: html_utils.py parses every ticket body with BeautifulSoup before anything downstream sees it
  • Embeddings & similarity: embed.py encodes every ticket with the open-source sentence-transformers/all-MiniLM-L6-v2 model; every query is compared by cosine similarity
  • SQL keys & upserts: every table after the landing zone is keyed on a natural id and upserted with ON CONFLICT ... DO UPDATE
  • Vector databases: ticket_embeddings is a pgvector column with an HNSW index; vector_store.py pushes the whole search into one SQL query
  • Docker & docker-compose: docker-compose.yml brings up Postgres+pgvector as one disposable, reproducible service
