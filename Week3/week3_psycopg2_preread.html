DB Connections with psycopg2

sample_data_loader.py already does all of this — psycopg2.connect(...), a cursor, execute(), commit(). This pre-read is what those calls actually mean, so the script reads as logic instead of incantation. The two words to get solid on: connection and cursor — they are not the same thing, and mixing them up is where almost every confusing psycopg2 bug comes from.

The phone line and the conversation

A connection is a live network session to Postgres — one authenticated socket, open for as long as the object exists, that also tracks your current transaction. A cursor is bound to one connection and is what actually sends SQL and reads results back. Think of the connection as the phone line, and the cursor as the person talking on it — you can have more than one conversation (cursor) on the same line (connection), and they all share whatever's been said so far (the transaction).

Try it: the lifecycle, traced

Opens the socket and authenticates. One Connection object = one Postgres session, with its own transaction state.

import psycopg2

conn = psycopg2.connect(
    host="localhost", port=5432,
    dbname="ride_prod", user="postgres", password="...",
)

A cursor is bound to one connection. You can open several — they all share that connection's transaction, so one cursor can see another's uncommitted work.

cur1 = conn.cursor()
cur2 = conn.cursor()

cur1.execute("INSERT INTO trips (driver_id, fare) VALUES (5, 200)")
cur2.execute("SELECT count(*) FROM trips")  # sees cur1's uncommitted insert too

conn.commit()  # commits BOTH cursors' work -- it's conn's transaction

execute() sends the query; results sit inside the cursor until you pull them out. The cursor remembers its position — fetch the same results twice and the second call comes back empty.

cur.execute("SELECT trip_id, fare FROM trips ORDER BY trip_id")
first  = cur.fetchall()
second = cur.fetchall()

Nothing written through a cursor is visible to any other connection until conn.commit(). autocommit is False by default — every statement waits.

try:
    cur.execute("INSERT INTO trips (driver_id, fare) VALUES (9, 500)")
    conn.commit()
except Exception:
    conn.rollback()
    raise

with conn: doesn't do what it looks like it does

with conn: manages the transaction — it commits on a clean exit, or rolls back if an exception propagates out of the block. It does not close the connection. That's still your job.

with conn:
    with conn.cursor() as cur:
        cur.execute("INSERT INTO trips (driver_id, fare) VALUES (77, 222)")
# transaction is committed here

print(conn.closed)   # 0 -- still open!
print(cur.closed)    # True -- the cursor's own "with" DID close it

conn.close()          # you still have to do this yourself
⚠️
with conn: and with cur: clean up two different things. This is exactly why db_report_starter.py wraps everything in try / finally: conn.close() instead of relying on with conn: alone.

Never build SQL with string formatting

The second argument to execute() exists so a value is sent to Postgres separately from the SQL text — Postgres always treats it as data, never as part of the command, no matter what characters it contains. Skip that, and a value the user controls can rewrite your query.

unsafe — f-string
driver_id_input = "1 OR 1=1"  # attacker-controlled input

sql = f"SELECT * FROM trips WHERE driver_id = {driver_id_input}"
cur.execute(sql)
# actual SQL sent: ...WHERE driver_id = 1 OR 1=1
# returns EVERY row in the table, not one driver's trips
safe — parameterized
cur.execute(
    "SELECT * FROM trips WHERE driver_id = %s",
    (driver_id_input,),
)
# psycopg2.errors.InvalidTextRepresentation:
# invalid input syntax for type integer: "1 OR 1=1"
# fails safely instead of running -- exactly what you want

Both examples above are real, verified psycopg2 output — the unsafe version really does return every row, and the safe version really does reject the malicious input with a clean error instead of executing it.

Common mistakes

MistakeWhat goes wrongFix
Building SQL with an f-string / % / .format()SQL injection, and it breaks on any value containing a quoteAlways pass values as the second argument: cur.execute(sql, (value,))
Assuming with conn: closes the connectionIt only commits/rolls back — the socket stays open, leaking connections over timeStill call conn.close(), typically in a finally block
Calling fetchall() twice, expecting the same rowsThe cursor already consumed them — the second call returns []Store the result in a variable the first time
Forgetting conn.commit() after an INSERT/UPDATEThe write appears to succeed with no error, but is invisible to everyone else and vanishes when the connection closesautocommit is False by default — commit explicitly, or set conn.autocommit = True if that's really what you want
Opening a new connection per query, inside a loopEach connection is a real network handshake — doing it per-row is slow and can exhaust the database's connection limitOpen one connection, reuse its cursor(s) for the whole batch
